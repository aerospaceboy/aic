# BC 全链路耗时诊断（2026-09-15）

## 目标与反馈环

为拆解 BC 长耗时，先比较 6 个历史单轮日志，再新增
`tools_demo/scripts/mission_timing_analysis.py`。工具直接解析 `launch.log` 中的
mission state、nav start/result、NearSlow、RPP collision 和预转参数，不改变
控制逻辑。推荐命令：

```bash
python3 tools_demo/scripts/mission_timing_analysis.py \
  /path/to/fast/launch.log /path/to/slow/launch.log \
  --task BC --budget 290 --details
```

## 291.1 秒根因

慢样本的 `red_cube_4 -> B` 明确使用三段
`(-2.20,-1.00),(-2.20,-6.00),(-0.40,-12.00)`，并在首个 1.38 m 目标上发生
4 秒预转超时；该腿 28.3 秒。当前源码不调用该 helper，直接路线同腿为
16.8--17.0 秒。因此 291.1 秒是一次已撤销的 A/B 实验结果，不是当前直接
路线的随机性能回退。

已在 `test_costudio_300s.py` 增加回归契约，禁止活动 `task_navigator.py`
导入或调用 `b_central_south_waypoints`。helper 保留用于历史几何对照，但不能
进入活动导航。

## 剩余时间与风险

最新 279.4 秒样本首块扫描动作成功但检测器未返回目标，经历一次正常重试、
一次重新对齐扫描和严格槽位回退，比 271.4 秒样本首扫识别多约 4.4 秒。
该恢复仍受可达/横向窗口及真实抓取窗口保护，缺少缩短它而不降可靠性的证据，
因此本轮没有修改感知安全链，也没有修改速度、NearSlow 比例或安全窗口。

## 2026-09-15 顺序优化实测

速度实验 `desired_linear_vel=1.80` 在同一环境退化到 338.6 秒，已恢复
1.65；因此没有通过提高速度或放宽 NearSlow 来换取时间。随后只改 BC 单题
`3rB_2bC` 的红方顺序：

```text
RED_CUBE_1/east -> RED_CUBE_4/west -> RED_CUBE_2/west
-> BLUE_CUBE_3/west -> BLUE_CUBE_2/east
```

该轮由结构化任务计划触发同一协调器状态机（外部 LLM 解析服务当时卡在
waiting_for_task，未把解析等待计入任务耗时），完整 5/5、skipped=0，耗时
265.0 秒。相对 279.9 秒同环境对照节省 14.9 秒（5.3%），相对 271.4 秒
基准节省 6.4 秒。单块耗时为 r1 65.9、r4 46.5、r2 67.8、b3 40.4、
b2 44.4 秒；5 个 `delivery_truth` 均 `valid=True`，日志无碰撞故障行。
速度、抓取/携带、BodyStop、NearSlow 和场景坐标均未改变。

随后用真实 LLM 竞赛入口做确认轮 `manual-20260915T114041`：同一顺序完成
`5/5`、`skipped=0`，总时长 `255.7s`，零抓取失败、零导航重试、零碰撞，
`minimum_clearance=0.1908m`、`safe=True`。两轮均低于 270 秒，因此该顺序
优化可以保留；仍建议在完整九轮中观察跨题型影响。

诊断时还发现上一轮完成后的 Gazebo/ROS 进程已空转约 12.9 小时，`gzserver`
与 coordinator 合计持续占用约 70% CPU，且 `/clock` 不再发布。已用项目自带
`CLEAN_ONLY=True tools_demo/scripts/clean_launch.sh` 清理，避免污染后续性能轮。
