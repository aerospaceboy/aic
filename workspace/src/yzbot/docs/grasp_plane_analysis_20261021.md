# 夹取不在固定垂直平面内的原因分析

本轮只分析，没有修改机械臂、导航、调度或控制参数，没有执行抓放或移动机器人。使用已有三轮日志、生产函数的离线重放，以及在线只读IK、运动规划、FK查询。证据位于 `/home/ros/ceshi2/项目分析/夹取倾斜分析-20261021/`。控制源码与上一轮最终收据核对一致。

## 判断

代码中存在两种不同的“斜”：

1. **下降轨迹斜**：到达预抓取点后，程序修改抓取目标X/Y，再从原位置直接下降，形成横移与下降同时发生的轨迹。这一点有直接代码和运行日志证据。
2. **接近时整臂侧摆或夹爪转动**：预抓取使用关节空间规划，没有要求整条路径在同一垂直平面中。扫描姿态本身包含侧向及腕部旋转；切换到抓取姿态时会出现侧摆和转腕。只读规划样例支持这一机制，但不是对某一历史视频的精确重建。

另外，若指的是“夹爪闭合瞬间本体仍明显歪斜”，现有日志没有记录该瞬间的完整末端四元数和关节轨迹，不能直接认定已经测得这种姿态偏差。

## 1. 下降前修正目标，但没有先到修正后的预抓取点

协调器在 `mission_coordinator.py:_send_manipulation_request` 中生成：

```text
pick      = (x, y, z)
pick_safe = (x, y, z + 0.070)
```

最初两点X/Y相同，符合竖直下降。实际执行顺序却是：

```text
move_to_pose(原pick_safe)
refine_pick_target_before_descend()  # 修改pick、pick_safe的X/Y
cartesian_move(修正后的pick)          # 没有先移动到新的pick_safe
```

修正函数更新了 `self.pick_safe_pose`，但只更新变量，未执行移动。底盘此时已固定，机械臂仍在原来的预抓取点，因此后续单个笛卡尔目标包含X、Y和Z的变化。固定末端朝向不会让这条空间直线自动变成竖直直线。

生产函数离线重放结果如下，基础绝对坐标为示例，修正量来自实际红2日志：

| 状态 | X | Y | Z |
| --- | ---: | ---: | ---: |
| 已到达的原预抓取点 | 0.34000 | 0.00100 | 0.12160 |
| 更新变量后的新预抓取点 | 0.34348 | 0.00855 | 0.12160 |
| 下一条下降请求的终点 | 0.34348 | 0.00855 | 0.05160 |

重放确认修正函数没有调用任何移动方法。该示例指令同时横移约8.31毫米、下降70毫米；几何倾角约6.77°。这里是指令几何，不是实测末端跟踪角度。

## 2. 预抓取阶段用了抓取后的Z窗口，导致修正频繁触发

`refine_pick_target_before_descend()` 在预抓取高度调用 `position_within_window(relative, GRASP_XY_LIMIT, GRASP_Z_LIMITS)`。当前窗口为：

```text
|x| <= 0.035 m，|y| <= 0.035 m，0.010 <= z <= 0.090 m
```

预抓取位置比实际抓取点高70毫米，物块在link6坐标中的Z自然与抓取后不同。最近三轮的15次抓取，预抓取时的X/Y均通过上述窗口，而Z均高于0.090米。于是没有进入直接通过分支，而是进入：

```text
correction_x = 0.014 - relative_x
correction_y = relative_y + 0.009
```

这里还包含经验参考位置 `(0.014, -0.009)`，所以即使视觉位置和X/Y已经相当准确，也会产生数毫米的侧向修正。例如 `relative_y=-0.00145` 时，仍增加约7.55毫米Y修正。问题不是“测到任何误差都不应修正”，而是判据没有分清预抓取与最终抓取阶段，且修正后的运动没有分段。

受控日志：

- `manual-20261021T114517`：5次修正；
- `manual-20261021T115553`：5次修正；
- `manual-20261021T120539`：5次修正。

这15次的指令水平修正量为7.59–11.40毫米，按70毫米名义下降量计算，相对竖直方向约6.19°–9.25°。这三轮没有触发 `pick_descend_fallback` 或抓取失败后的 `grasp_correction`，因此不需要用罕见回退解释这批普遍存在的斜降。

## 3. 末端向下不等于整臂在车体的同一垂直平面中

正式任务的抓取目标四元数为 `(x,y,z,w)=(0,1,0,0)`，对应工具+Z轴向下。请求发送和接收代码均保持这个顺序；`grasping_frame` 与 `link6` 在URDF中没有额外固定旋转。

但 `move_to_pose()` 先用当前关节状态求IK，再调用 `move_to_joint_target()`，后者只给MoveGroup最终关节约束，没有路径平面约束，也没有要求肩部joint1或腕部joint4在全过程固定。

初始扫描姿态与抓取姿态不同，扫描目标Y为-0.030米，工具轴相对竖直约偏11.16°。只读样例先求扫描IK，再从该状态规划至 `(0.34, y, 0.1216)`，抓取朝向仍为 `(0,1,0,0)`：

| 示例目标Y | IK终点肩部joint1 | IK终点腕部joint6 |
| --- | ---: | ---: |
| 0.001m | 0.17° | 0.17° |
| 0.010m | 1.68° | 1.68° |
| 0.040m | 6.71° | 6.71° |

扫描样例joint1约-6.95°、joint4约6.63°、joint6约-31.71°。接近目标时这些关节发生变化，视觉上会看到手臂从侧面收正、腕部旋转。FK样例的目标末端仍近似竖直，说明肩部侧转与末端向下可以同时成立。0.040米是用于区分机制的示例横向偏移，不是声称三轮中真实残差达到此值。

代码允许目标带非零Y；底盘对中也有容差。因此如果要求“始终处于车体固定XZ平面”，还需要控制横向残差和整臂运动平面，单改工具四元数无法保证。

## 4. 两个次要来源及证据边界

**笛卡尔失败后回退到关节规划。**当前 `run_pick_only()` 中，下降笛卡尔规划失败两次，会执行 `move_to_pose(..., "pick_descend_fallback")`。这条路线不保证末端直线下降或同平面运动，可能造成更明显的绕行。它在代码中存在，但上述三轮没有触发，不能把它当成本批主要原因。

**底盘对正误差与目标横向偏移。**底盘航向对齐有容差，抓取前的目标还可能经过视觉/静态货位选择及侧移对中。上述15次记录的底盘航向残差最大约1.98°，会叠加世界坐标下的夹取方向偏差，但不能解释所有侧摆。现有位置安全窗口也不检查夹爪相对物块的朝向，所以“抓取窗口通过”不等于“全程垂直平面夹取”。

独立运行机械臂节点时还有一个需区分的配置：节点旧默认 `tool_orientation=[0,0.9939,0,-0.1100]` 本身略倾斜；正式持久任务会被协调器请求的 `(0,1,0,0)` 覆盖。本次没有证据表明旧默认泄漏到了正式抓取。

## 后续应先验证什么

建议按动作阶段记录预抓取到位、修正后、下降结束、夹爪闭合前的真实TCP位置/四元数、joint1/4/6、底盘姿态及物块姿态，并与指令点分开。这样能把“横向斜降”“整臂侧摆”“闭合时夹爪本体倾斜”分别量化。

若进入修复，优先处理：先在安全高度完成X/Y修正，再独立竖直下降；同时区分预抓取高度判据与最终抓取窗口。之后再根据目标明确是否要求固定车体垂直平面，设计接近段和关节/姿态约束，并约束关节规划回退。不能只放宽抓取窗口、增大夹爪闭合量或把速度调低来掩盖轨迹问题。

以上为分析结论，尚未实施这些修复。只读规划不是物理实测，也没有新跑搬运轮次。
